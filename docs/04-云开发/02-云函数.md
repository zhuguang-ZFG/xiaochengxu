# 云函数

## 为什么读这篇

云函数是云开发的「后端逻辑」载体：跑在小程序之外的服务端代码。前端不该做的（密钥、聚合、跨域代理）都放这里。这篇讲透：云函数怎么写、怎么调、怎么拿用户身份、怎么定时跑。

前置知识：[云开发入门](../04-云开发/01-云开发入门.md)（已开通环境、init 完成）。

## 云函数是什么

调用链路演示（渲染示意图动画：小程序端 callFunction → 云函数处理 → 云数据库操作 → 结果返回）：

![云函数调用链路演示](../assets/demo-callfunction.gif)

一段跑在腾讯云 Node.js 环境里的函数，特点：

- **免部署服务器**：右键上传即部署，平台托管
- **按调用计费**：无调用不计费（免费额度内）
- **与小程序天然打通**：`wx.cloud.callFunction` 调用，`cloud.getWXContext()` 拿用户身份
- **适合**：业务逻辑、数据库聚合、第三方 API 代理、定时任务

不适合：长连接（WebSocket）、超长任务（平台有执行时长限制，默认几秒~几十秒级）。

## 创建与部署

项目根目录建 `cloudfunctions/`，每个函数一个目录：

```text
cloudfunctions/
└── getTodoList/
    ├── index.js
    └── package.json   # 依赖声明（如需要 npm 包）
```

**index.js 最小结构**：

```js
// cloudfunctions/getTodoList/index.js
const cloud = require('wx-server-sdk');
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV });  // 用调用方环境

exports.main = async (event, context) => {
  // event：小程序端传来的参数
  // context：运行信息（函数名、内存等）
  return {
    code: 0,
    data: '云函数返回值'
  };
};
```

部署方式（开发者工具）：

1. `cloudfunctions/` 目录上右键 → **创建 Node.js 云函数**
2. 写完代码，目录右键 → **上传并部署（云端安装依赖）**
3. 有依赖时选「云端安装依赖」，本地装的 node_modules 不用传

也可以在控制台在线编辑/部署。

## 参数传递与返回值

![云开发调用链路](../assets/diagram-cloud-callchain.png)

**小程序端调用**：

```js
wx.cloud.callFunction({
  name: 'getTodoList',
  data: { page: 1, size: 20 },      // 传给 event
  success(res) {
    console.log(res.result);         // 云函数 return 的值
  },
  fail(err) { console.error(err); }
})
```

**云函数端接收**：

```js
exports.main = async (event, context) => {
  const { page = 1, size = 20 } = event;
  // ...业务逻辑
  return { code: 0, list: [...], total: 100 };
};
```

规则：

- 传入：`data` → `event`（自动 JSON 序列化）
- 传出：`return` 的值 → `res.result`（可序列化的对象）
- 错误处理：云函数内 throw 会在小程序端走 `fail` 回调（errMsg 带信息）

```js
// 云函数内主动报错
if (!openid) {
  throw new Error('未登录');
}
```

## 获取用户身份：cloud.getWXContext()

云函数内**免鉴权**拿到当前调用用户：

```js
exports.main = async (event, context) => {
  const wxContext = cloud.getWXContext();
  // {
  //   openid: 'oXXXX...',      // 用户唯一标识（核心身份）
  //   appid: 'wxXXX...',
  //   unionid: 'oYYYY...'      // 开放平台统一身份（企业主体才有）
  // }
  return { openid: wxContext.openid };
};
```

用途：

- 数据归属：写库时存 openid，查询只查自己的数据
- 免登录：不需要 wx.login + code2session 那套（[网络请求与数据](../03-进阶/03-网络请求与数据.md) 里自建后端的登录在这里被简化掉了）
- 注意：**openid 不能伪造**（由微信侧注入），这是云开发安全性的根基

## 定时触发器

云函数除了被小程序调用，还能**定时执行**（如每日统计、定时清理）。在函数目录建 `config.json`：

```json
{
  "triggers": [
    {
      "name": "dailyStat",
      "type": "timer",
      "config": "0 0 3 * * * *"
    }
  ]
}
```

cron 格式（7 段：秒 分 时 日 月 周 年），`0 0 3 * * * *` = 每天凌晨 3 点。

部署后在控制台可看到触发器；定时触发时 `event` 为触发信息（非小程序参数），且 `getWXContext().openid` 为空（没有具体用户）。

## 云函数运行机制

### 冷启动与容器生命周期

云函数运行在**临时容器**中，不是一直在线的服务：

- **容器回收**：一段时间无请求（通常 5-10 分钟空闲）后，容器被平台回收。下次请求触发**冷启动**：分配新容器 → 启动 Node.js 运行时 → 加载依赖 → 执行 `exports.main`
- **顶层代码只执行一次**：`const cloud = require('wx-server-sdk')` 和 `cloud.init()` 放在 `exports.main` 外面——它们只在冷启动时执行一次，后续热请求直接复用容器。这是把初始化放顶层的原因
- **量化**：冷启动通常 200-800ms（取决于依赖大小和 `node_modules` 数量），热路径 <5ms。免费额度下长空闲后首次调用用户会明显感知到延迟
- **优化策略**：减少顶层 `require` 的包数量（按需加载非关键模块）、利用容器复用缓存数据库连接（`const db = cloud.database()` 放顶层）、避免在顶层做同步 I/O

### 执行上下文与并发模型

- **`context` 参数**：`exports.main = async (event, context)` 的第二个参数包含运行时信息——`context.memory_limit_in_mb`（内存上限）、`context.function_version`（函数版本）、`context.request_id`（请求唯一 ID，排查问题必备）
- **无状态水平扩展**：同一函数可以同时运行在多个容器实例中（平台自动扩容）。**全局变量不跨实例共享**——用全局变量缓存数据库连接可以，但不要指望全局变量在两次请求之间保持状态
- **超时机制**：默认超时 3s（可在控制台配置到 20s）。超时后容器被**强制终止**，不执行 `finally` 回调。长任务（如批量数据处理）必须拆到异步队列或调大超时配置

### 身份注入的安全链路

`cloud.getWXContext()` 返回的 `openid` 为什么不能被伪造？

1. 小程序端调用 `wx.cloud.callFunction` 时，微信客户端用本地存储的 access token 附加身份凭证
2. CloudBase 运行时向微信认证服务验证 token 合法性
3. 验证通过后，微信认证服务把 `openid`/`unionid` 注入到云函数的运行上下文（`context.WX_CONTEXT`）
4. `cloud.getWXContext()` 只是读取这个注入值——整个过程不经过小程序前端代码

openid 由微信侧注入，小程序代码无法篡改。这是云开发安全模型的根基——也是为什么云函数内操作数据库「不受前端权限限制」（因为它已经知道调用者是谁）。

## 典型场景

### 场景一：数据库聚合（小程序端做不了的事）

小程序端云数据库查询能力有限（不能跨集合 join、聚合受限），复杂统计放云函数：

```js
const db = cloud.database();
exports.main = async (event) => {
  const { _ } = db.command;
  const res = await db.collection('orders')
    .aggregate()
    .group({ _id: '$status', count: $.sum(1) })
    .end();
  return res.list;
};
```

### 场景二：第三方 API 代理

小程序端有域名白名单限制（[网络请求与数据](../03-进阶/03-网络请求与数据.md)），云函数**没有**——可以请求任意 HTTPS 服务，还能藏密钥：

```js
exports.main = async (event) => {
  const res = await new Promise((resolve, reject) => {
    // 用 got / axios 或原生 https 请求第三方
    // 密钥（API Key）只写在云函数里，不外泄
  });
  return res.data;
};
```

### 场景三：写库前的安全校验

敏感写操作放云函数（权限设置宽松的集合也能被保护）：

```js
exports.main = async (event) => {
  const { openid } = cloud.getWXContext();
  const { content } = event;
  if (!content || content.length > 500) throw new Error('内容不合法');
  const db = cloud.database();
  await db.collection('messages').add({
    data: { openid, content, createTime: Date.now() }
  });
  return { code: 0 };
};
```

## 常见错误 / 避坑

1. **忘记 `cloud.init`**：函数里第一行就要 `cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })`，否则数据库操作报环境错误。
2. **本地调试与云端环境不一致**：本地调试用本地 node_modules，云端用「云端安装依赖」；依赖版本不一致导致线上行为不同，部署选云端安装。
3. **return 不可序列化内容**：返回 `undefined`/`NaN`/函数等会导致小程序端 res.result 异常；只返回纯对象。
4. **误以为小程序端能拿到 getWXContext**：`getWXContext` 只在云函数里可用，小程序端拿 openid 只能靠调用云函数返回。
5. **定时触发器改了不重新部署**：config.json 的 trigger 修改后需要重新上传部署才生效。
6. **云函数超时**：默认超时较短（几秒到几十秒，可配置），内部有长循环/慢第三方请求时提前超时；把慢逻辑拆到独立函数并调大超时配置。

## 随堂测验

**Q1**: 云函数中忘记写 `cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })`，会发生什么？
- [ ] A. 云函数正常执行，但返回值是 undefined
- [ ] B. 云函数无法被小程序端调用，报函数名找不到的错误
- [ ] C. 云函数能执行，但内部操作数据库时报环境错误
- [ ] D. 云函数会自动使用默认环境，不会出错

<details><summary>答案</summary>

**C**. 云函数第一行必须 `cloud.init`，否则函数本身能跑，但内部访问数据库/存储等云资源时会报环境错误，参见[常见错误](#常见错误--避坑)第 1 条。

</details>

**Q2**: 小程序端调用 `wx.cloud.callFunction({ name: 'add', data: { x: 1 } })`，云函数里如何拿到参数 `x`？
- [ ] A. 通过 `context.data.x`
- [ ] B. 通过 `event.x`
- [ ] C. 通过 `wx.cloud.getWXContext().x`
- [ ] D. 通过 `this.data.x`

<details><summary>答案</summary>

**B**. 小程序端 `data` 字段传的参数会自动 JSON 序列化后进入云函数的 `event` 对象，所以通过 `event.x` 获取，参见[参数传递与返回值](#参数传递与返回值)。

</details>

**Q3**: 一个云函数配置了每日凌晨 3 点的定时触发器，当定时触发执行时，`cloud.getWXContext().openid` 的值是什么？
- [ ] A. 最后一个调用该函数的用户 openid
- [ ] B. 管理员的 openid
- [ ] C. 空值（因为没有具体用户调用）
- [ ] D. 随机生成的临时 openid

<details><summary>答案</summary>

**C**. 定时触发器执行时没有具体用户，`getWXContext().openid` 为空，这是云函数定时触发的重要特性，参见[定时触发器](#定时触发器)。

</details>

**Q4**: 以下关于云函数返回值的说法，哪个是正确的？
- [ ] A. 可以返回函数对象，小程序端会自动序列化
- [ ] B. 返回 `NaN` 时小程序端会收到 `null`
- [ ] C. 只能返回可序列化的纯对象，否则小程序端 `res.result` 异常
- [ ] D. 返回 `undefined` 时小程序端会自动重试调用

<details><summary>答案</summary>

**C**. 云函数 return 的值必须是可序列化的对象，返回 `undefined`/`NaN`/函数等会导致小程序端 `res.result` 异常，参见[常见错误](#常见错误--避坑)第 3 条。

</details>

**Q5**: 为什么在云函数中通过 `cloud.getWXContext()` 拿到的 openid 不能被伪造？
- [ ] A. 因为 openid 是用 AES 加密传输的
- [ ] B. 因为 openid 由微信侧注入到运行上下文中，不经过小程序代码
- [ ] C. 因为 openid 需要配合密钥才能使用
- [ ] D. 因为云函数运行在隔离的沙箱环境中，外部无法访问

<details><summary>答案</summary>

**B**. openid 由微信侧在调用链中注入到云函数上下文，不经过小程序前端代码，因此无法被伪造，这是云开发安全性的根基，参见[获取用户身份](#获取用户身份cloudgetwxcontext)。

</details>

**Q6**: 云函数冷启动耗时 200-800ms，以下哪种做法**不能**优化冷启动性能？
- [ ] A. 把 `cloud.init()` 和 `const db = cloud.database()` 放在 `exports.main` 外面（顶层）
- [ ] B. 减少顶层 `require` 的依赖包数量
- [ ] C. 在 `exports.main` 内部每次调用时重新 `require` 所有依赖
- [ ] D. 利用容器复用，全局变量缓存数据库连接

<details><summary>答案</summary>

**C**. 在 `exports.main` 内部每次 `require` 所有依赖，意味着每次请求都重新加载模块，反而增加热路径开销。正确做法是把 `require` 和初始化放顶层（只在冷启动时执行一次），减少顶层依赖包数量，利用容器复用缓存连接，参见[冷启动与容器生命周期](#冷启动与容器生命周期)。

</details>
