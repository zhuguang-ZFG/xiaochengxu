# 第三方组件库：vant / TDesign

## 为什么读这篇

原生组件只覆盖最基础的控件（view/text/button/input）。真实项目里单元格、弹窗、下拉刷新、徽标、日历……全手写成本极高且样式不统一。**组件库**（vant-weapp、TDesign 等）是原生小程序的「半官方」解法：不改变原生架构，只提供高质量的现成组件。

这篇讲透：组件库怎么装（npm + 构建 npm 的机制）、怎么按需引入控制体积、怎么定制主题，以及和自定义组件的关系。

前置知识：[自定义组件](../03-进阶/02-自定义组件.md)（组件通信与样式隔离）、[项目结构](../01-入门/03-项目结构.md)。

## 一、选型：主流的两个

| 组件库 | 特点 | 官方入口 |
|---|---|---|
| [vant-weapp](https://vant-ui.github.io/vant-weapp/) | 有赞出品，组件最全、社区最大，经典选择 | `@vant/weapp` |
| [TDesign](https://tdesign.tencent.com/miniprogram/) | 腾讯官方设计体系，与微信视觉语言更一致 | `tdesign-miniprogram` |
| WeUI | 微信官方基础样式扩展（`extended` 扩展组件） | 微信官方扩展能力 |

选择建议：追求组件丰富度选 vant；追求腾讯设计语言一致性选 TDesign。两者用法几乎相同（都是 npm 包 + usingComponents 引入），学会一个另一个直接上手。

## 二、安装：为什么「构建 npm」这一步绕不开

以 vant-weapp 为例：

```bash
# 1. 项目根目录初始化 npm
npm init -y

# 2. 安装组件库（--production 只装运行时依赖）
npm i @vant/weapp -S --production

# 3. 关键一步：开发者工具 → 菜单「工具」→「构建 npm」
#    完成后项目根目录出现 miniprogram_npm/ 目录
```

```json
// app.json 或页面 json 里声明使用
{
  "usingComponents": {
    "van-button": "@vant/weapp/button/index",
    "van-field": "@vant/weapp/field/index"
  }
}
```

```xml
<!-- 页面里直接用 -->
<van-button type="primary" bindtap="onTap">保存</van-button>
<van-field value="{{title}}" placeholder="请输入待办" bind:change="onChange" />
```

### 2.1 机制：为什么不能直接 `require('@vant/weapp/...')`

这是新手最容易卡的一步。小程序**不能直接使用 node_modules**，原因：

1. **打包器不认识 node_modules 结构**：小程序代码包由微信打包器处理，它只识别小程序约定的目录结构（app.json/pages/组件），不会像 Webpack/Vite 那样解析 `node_modules` 里的依赖图。
2. **依赖不是自包含的**：npm 包之间相互 require、路径不完整（`../../lib/xxx`），打包器无法正确解析，直接引用会报「模块找不到」。
3. **构建 npm 就是「适配器」**：开发者工具读取 `package.json` 的依赖，把 `node_modules` 里的包**编译成小程序可识别的格式**，输出到 `miniprogram_npm/` 目录。之后 `usingComponents` 里的 `@vant/weapp/button/index` 就是指向 `miniprogram_npm/@vant/weapp/button/index` 的简写。

**推论**：`npm i` 之后必须点「构建 npm」，否则 usingComponents 会报「组件未找到」；依赖升级后要重新构建。构建产物 `miniprogram_npm/` 是**构建生成物**，不应手改。

## 三、按需引入：包体积是硬约束

小程序主包 ≤ 2M（[分包加载](https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages.html)），组件库全量引入可能直接吃掉上百 KB 甚至接近上限——**必须按需引入**。

vant 的引入天然是「按需」的：`usingComponents` 里只写用到的组件路径，打包器只把被引用的组件及其依赖编入包。两条原则：

1. **每个页面只声明用到的组件**，不要为了省事在 `app.json` 全局声明一大堆。
2. **公共高频组件**（如按钮、弹窗）才放 `app.json` 全局；低频组件（日历、图表）放页面级。

量化验证方法：开发者工具「详情 → 基本信息 → 代码包大小」，引入前 vs 引入后对比；生产构建看「代码包分析」。如果单页面只用 1 个组件，却把整个库拖进来，就是引入方式错了。

## 四、主题定制：CSS 变量机制

组件库的样式定制走 **CSS 变量**（Design Token）机制：组件内部样式引用 `var(--xxx)`，你在外层（`page` 或根节点）覆盖同名变量即可全局换肤：

```css
/* app.wxss */
page {
  --button-primary-background-color: #07c160;   /* 主按钮背景 */
  --button-primary-border-color: #07c160;
  --dialog-border-radius: 16rpx;
}
```

**机制要点**：CSS 变量在「作用域链」上可继承覆盖，组件内部 `var(--x)` 会向上查找最近的定义——所以**在 `page` 上定义一次，全局生效**；在具体页面/组件内定义，只影响局部。这就是「一套组件库、多套主题」的机制基础（与 [自定义组件](../03-进阶/02-自定义组件.md) 的样式隔离配合使用）。

> 注意：vant 部分组件用 `externalClasses`（外部样式类）而不是 CSS 变量控制特定细节，如 `custom-class`。遇到样式改不动时，先查组件文档支持的是变量还是外部样式类。

## 五、与自定义组件/原生组件混用

- **组件库组件可以互相嵌套**：`van-field` 放进 `van-cell-group`，自己写的组件里也能用 `van-button`。
- **事件通信**：组件库事件名与原生不同，vant 用 `bind:change` 风格（冒号前缀），和自定义组件的 `triggerEvent` 是同一条通道。
- **样式隔离**：组件库样式默认隔离（`styleIsolation: isolated`），你页面的 wxss 直接选择器改不动库组件内部；用 CSS 变量或外部样式类，别用 `!important` 硬碰。

## 常见错误 / 避坑

1. **装了 npm 包不点「构建 npm」**：报「组件未找到」/「找不到模块」；工具菜单手动构建，依赖变更后重构建。
2. **全量引入组件库**：主包体积暴涨，接近 2M 上限时上传失败；按需声明 usingComponents。
3. **用页面选择器硬改库组件内部样式**：样式隔离挡掉；改用 CSS 变量 / externalClasses。
4. **项目没有 package.json 就 npm i**：先 `npm init -y`；构建 npm 依赖合法的 package.json。
5. **升级依赖后不重新构建**：miniprogram_npm 是旧产物；`npm i` 后必须重建。
6. **组件库与基础库版本不匹配**：老组件库在低基础库上 API 缺参；按项目最低支持的基础库选组件库版本（README 看组件库兼容说明）。

## 随堂测验

**Q1**: 开发者执行了 `npm init -y` 和 `npm i @vant/weapp -S --production`，然后在页面 json 里用 `usingComponents` 引入 van-button，编译后报「组件未找到」。最可能的原因是什么？
- [ ] A. vant-weapp 不支持当前基础库版本
- [ ] B. 没有在开发者工具里执行「工具 → 构建 npm」，miniprogram_npm 目录还没有生成
- [ ] C. usingComponents 的路径写法错误，应该写 node_modules 的完整路径
- [ ] D. 需要先 import 组件库的 JS 文件才能使用

<details><summary>答案</summary>

**B**. 小程序不能直接使用 node_modules，必须通过「构建 npm」将 node_modules 编译成小程序可识别的格式输出到 `miniprogram_npm/`；npm 安装后不构建，组件路径无法解析。

</details>

**Q2**: 想要把组件库的主按钮颜色改成品牌色 `#07c160`，正确的做法是什么？
- [ ] A. 在页面 wxss 里用 `.van-button--primary { background: #07c160 !important; }` 强制覆盖
- [ ] B. 在 `page` 选择器上通过 CSS 变量覆盖，如 `--button-primary-background-color: #07c160`
- [ ] C. 修改 miniprogram_npm 里组件库的源码
- [ ] D. 组件库的样式完全不可定制

<details><summary>答案</summary>

**B**. 组件库通过 CSS 变量（Design Token）实现主题定制，在 `page` 上覆盖变量即可全局生效；组件库样式默认隔离，用页面选择器直接改会被挡住。

</details>

**Q3**: 关于组件库的按需引入，以下哪种做法是正确的？
- [ ] A. 在 app.json 的 usingComponents 里声明所有组件库组件，方便全局使用
- [ ] B. 高频公共组件放 app.json 全局声明，低频组件放各页面 json 单独引入，避免包体积膨胀
- [ ] C. 按需引入需要特殊的构建配置，默认不支持
- [ ] D. 组件库体积很小，全量引入也不会超过 2M 限制

<details><summary>答案</summary>

**B**. 主包 ≤ 2M 是硬约束，全量引入组件库可能吃掉上百 KB；应高频组件全局声明、低频组件页面级引入，用代码包分析工具量化验证。

</details>

**Q4**: 关于 `miniprogram_npm` 目录，以下说法正确的是？
- [ ] A. 它是源代码的一部分，需要提交到 git 仓库
- [ ] B. 它是「构建 npm」后的产物，可以手动编辑来满足定制需求
- [ ] C. 它是构建生成物，不应手动编辑；依赖更新后需要重新构建
- [ ] D. 它只在云开发环境下才会生成

<details><summary>答案</summary>

**C**. `miniprogram_npm/` 是构建 npm 的产物，不应手改；npm 依赖变更后必须重新构建以更新产物。

</details>
